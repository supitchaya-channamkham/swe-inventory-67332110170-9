- **ข้อเสนอแนะในการแก้ไข:** ปรับเงื่อนไขเป็น `low <= item.price <= high` เพื่อให้รวมราคาที่ขอบเขตตามข้อกำหนด

### [5] เมธอด: `concurrent_restock`
- **หมวด/ระดับความรุนแรง:** Concurrency (Correctness) / High
- **ปัญหาคืออะไร:** เกิด Race Condition ชนิด Lost Update เนื่องจากมีการอ่านค่าปัจจุบัน `current = self._inv._items[name].quantity` ไว้นอกบล็อก `with self._lock:` เมื่อมีหลาย Thread เรียกพร้อมกัน ทั้งสอง Thread จะอ่านค่าตั้งต้นเดียวกัน แล้วนำไปเขียนทับกันในล็อก
- **กรณีที่ทำให้พัง (Input ตัวอย่าง):**
  - สินค้าเดิมมี 10 ชิ้น
  - Thread 1 และ Thread 2 สั่งเติมคนละ 5 ชิ้นพร้อมกัน
  - ทั้งสอง Thread อ่าน `current = 10` ออกไปก่อนเข้าล็อก
  - Thread 1 เข้าล็อก คำนวณ `10 + 5 = 15` แล้วบันทึก
  - Thread 2 เข้าล็อกต่อมา คำนวณ `10 + 5 = 15` แล้วบันทึกทับ
  - ผลลัพธ์: สต็อกกลายเป็น 15 ชิ้น แทนที่จะเป็น 20 ชิ้น (ยอดเติมหายไป 5 ชิ้น)
- **ข้อเสนอแนะในการแก้ไข:** ย้ายคำสั่งการอ่านค่าและบวกเพิ่มเข้าไปไว้ภายในบล็อก `with self._lock:` ทั้งหมด หรือล็อกก่อนเรียกเมธอด `restock()` เดิม

### [6] เมธอด: `average_unit_value`
- **หมวด/ระดับความรุนแรง:** Correctness / High
- **ปัญหาคืออะไร:**
  1. ตัวหารผิดความหมาย Docstring ระบุ "มูลค่าเฉลี่ยต่อชิ้น" (Per Unit) แต่โค้ดใช้ `len(self._inv._items)` ซึ่งเป็นจำนวนประเภทสินค้า (SKU)
  2. ไม่มีการป้องกันกรณีคลังสินค้าว่างเปล่า ทำให้เกิด `ZeroDivisionError`
- **กรณีที่ทำให้พัง (Input ตัวอย่าง):**
  - มีสินค้า A จำนวน 10 ชิ้น ราคาชิ้นละ 100 บาท (มูลค่ารวม 1,000 บาท) เฉลี่ยต่อชิ้นควรได้ 100 บาท แต่โค้ดคำนวณ `1000 / 1 = 1000.0` บาท
  - หากคลังว่าง (`len == 0`) โปรแกรมจะแครชทันทีด้วย `ZeroDivisionError: division by zero`
- **ข้อเสนอแนะในการแก้ไข:** คำนวณหาจำนวนชิ้นรวมทั้งหมด (`total_units = sum(item.quantity for item in self._inv._items.values())`) และเพิ่มเงื่อนไขตรวจสอบหาก `total_units == 0` ให้คืนค่า `0.0` ทันที
